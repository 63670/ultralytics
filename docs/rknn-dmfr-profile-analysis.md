# DMFR RKNN 逐层报告分析（2026-10-16）

来源：用户提供的 `Layer Profiling (Layer Time & Target Hardware NPU/CPU)` 文本。
该附件没有模型 SHA256、Toolkit/runtime 版本和频率信息；模块归属依据 FullName 对照本仓库配置。
输入为 UINT8、batch=1、640×640；包含 DME 方向分支、两处 CAFR，以及瑞芯微兼容的九输出检测头。

## 汇总核对

逐行解析 ID 0–159 共 160 个算子，Time(us) 之和为 590,470 us，与报告总计完全一致。

| 执行位置 | 算子数量 | 耗时（ms） | 占逐层总耗时 |
| --- | ---: | ---: | ---: |
| CPU | 22 | 442.856 | 75.00% |
| NPU | 138 | 147.614 | 25.00% |
| 合计 | 160 | 590.470 | 100.00% |

这是逐层性能分析口径。590.470 ms 的倒数约为 1.69 次/秒，只能用于理解本报告量级，
不能替代关闭 perf_debug 后的正式模型延迟或系统 FPS。官方参考也注明逐层 profiling 可能低于实际性能：
[连板性能示例](https://github.com/airockchip/rknn-toolkit2/blob/master/rknn-toolkit2/examples/functions/npu_device_test/README.md)。

两处 CAFR 共 536.562 ms，占 90.87%。除输入输出的 0.406 ms 外，所有 CPU 耗时都位于 CAFR。
`/direction/` 对应的 DME 新增方向分支合计 15.943 ms，均在 NPU 上；这不代表 DME 无额外延迟。

## 最大瓶颈是布局转换，不是 Softmax

| CPU 算子类别 | 次数 | 合计（ms） | 占全图 |
| --- | ---: | ---: | ---: |
| Transpose | 4 | 225.535 | 38.20% |
| Reshape | 6 | 208.681 | 35.34% |
| exSoftmax13 | 2 | 8.234 | 1.39% |

Transpose 和 Reshape 合计 434.216 ms，占 73.54%。只替换 Softmax 无法解决主要开销。
最慢的单算子包括：

| ID | Target | FullName | 耗时（ms） |
| --- | --- | --- | ---: |
| 96 | CPU | `Transpose:/model.13/Transpose_2` | 118.767 |
| 103 | CPU | `Reshape:/model.13/Reshape_2_output_0_rs` | 117.691 |
| 74 | CPU | `Transpose:/model.10/Transpose_2` | 63.889 |
| 81 | CPU | `Reshape:/model.10/Reshape_2_output_0_rs` | 60.590 |

报告确认了这些具体编译节点在 CPU 执行，不等于证明所有 Transpose/Reshape 均不受 NPU 支持。
目前证据也不能将该现象与每条 `Unkown op target: 0` 编译消息一一对应。

CAFR 的邻域展开和重组需要把 `[1,256,20,20]` 或 `[1,128,40,40]` 的特征转成包含 25 个邻域值的表示。
编译图把通道/邻域维度映射为 `(256,25,40,40)`、`(128,25,80,80)` 等形式。
其中的布局适配及 CPU/NPU 边界值得优先处理；不能按 PyTorch view 的低成本来估算这些编译节点。
报告本身无法进一步分离重排、拷贝和同步各自的时间。

## NPU 侧也有显著开销

两处 CAFR 的 Mul 合计 53.785 ms，重组 ReduceSum 被映射为 Conv，合计 18.674 ms；
它们都在 NPU 上。仅消除 CPU 执行、保持其余节点耗时不变，仍会留下报告中的 147.614 ms NPU 时间。
因此不能据此保证“全部搬到 NPU 就满足 10 FPS”。
同样，去掉 CAFR 后余项的 53.908 ms 也不是替换后模型的预测延迟：替换操作本身有成本，
编译融合、数据依赖和 profiling 开销也可能改变。

报告的 Total Memory Read/Write Per Frame Size 为 319,058 KB，表示报告统计的每帧读写量，
不是模型峰值内存占用。

## 后续处理顺序

1. 保留现有训练 checkpoint、九输出导出和该原始性能报告，避免边改训练结构边改导出而失去对照。
2. 如要保留 CAFR，优先研究保持浮点计算等价的部署表示，针对邻域布局转换、大张量乘加和归约，
   尽量避免将通道映射成大 batch 及高维中间表示。必须分别验证数值一致性、编译后的 Target 和实际耗时。
3. 可按 `model.10`、`model.13` 分别做只用于测速的旁路实验，定位实际增量；旁路改变网络输出，不能继承原模型 AP。
4. 等价实现仍达不到预算时，再讨论替换重组机制；改变机制或重组核大小通常需要重新训练和评估。
5. 最终统一 batch、校准数据、SDK/runtime、频率与散热，用关闭 perf_debug 的结果报告板端模型延迟。

本轮完成了报告解析和归因，没有修改模型结构、导出算法或论文中的性能结论。
